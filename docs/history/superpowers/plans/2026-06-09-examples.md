# Example Services (Sub-project 6) Implementation Plan

> REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Integration-heavy; verify lib/codegen APIs and adapt. Docker required (Redpanda + Postgres). These are DELETABLE demos under `examples/` — they prove the platform end-to-end; `platform/` must never import them.

**Goal:** Demonstrate the whole platform with a realistic event-driven CQRS choreography: an HTTP gateway accepts orders, services react via Kafka, and the gateway serves a read model built from events.

**Flow (the demo):**
```
client → POST /orders (gateway, REST, oapi-codegen, auth)
  gateway → publish CreateOrderCommand → topic "orders.commands"  (returns 202 + order id)
orders svc → consume orders.commands (inbox dedup)
  → CQRS command CreateOrder: pipeline [Logging,Tracing,Metrics,Validation,Transaction,Audit] →
     handler writes orders row + enqueues OrderCreated to outbox (same tx)
  → outboxkafka relay drains outbox → topic "orders.events"
payments svc → consume orders.events (OrderCreated, inbox dedup)
  → CQRS command ProcessPayment: writes payments row + outbox PaymentProcessed (same tx)
  → relay → topic "payments.events"
notifications svc → consume payments.events (PaymentProcessed, inbox dedup) → mock notify (log)
gateway projection → consume orders.events + payments.events → upsert orders_read(order_id,status,...)
client → GET /orders/{id} (gateway) → served from orders_read projection (status: created → paid)
```

**Architecture:** Each service is `examples/<svc>/cmd/<svc>/main.go` (manual DI wiring all platform pieces + run.Closer) + `internal/` (transport=consumers/handlers, app=command/query handlers, domain, store=sqlc). DB-per-service (separate DB each, one Postgres instance locally). Commands+events are protobuf (`proto/orders/v1`). Services consume with cooperative-sticky groups + inbox dedup; emit via outbox→outboxkafka relay.

**Depends on:** ALL platform packages (SP1-SP5) + proto/gen.

## Task 2 — orders service (command consumer → outbox)
- DB: `examples/orders/migrations` — `orders(id uuid pk, customer_id, amount_cents bigint, currency, status text, created_at)` + the outbox table (reuse `platform/outbox` schema — copy its DDL into orders migrations) + the inbox table (copy `platform/inbox` DDL).
- sqlc: `InsertOrder`, `GetOrder`.
- app: `CreateOrderCommand` handler — writes order row (status="created") via sqlc (using pg.FromContext tx) + `outbox.Repository.Enqueue(OrderCreated proto bytes, aggregateType="orders.events", aggregateID=order_id)`. Wrapped with cqrs `Decorate(handler, Logging, Tracing, Metrics, Validation, Transaction(pool), Audit(store,"order:create",...))`.
- transport: kafka consumer on "orders.commands"; per message: `inbox.ProcessOnce(pool, "orders", msgID, func(ctx){ decode CreateOrderCommand; dispatch through the decorated handler })` — NOTE the inbox ProcessOnce already opens a tx (RunInTx); the Transaction behavior nests via savepoint (SP2). Alternative: drop the Transaction behavior here and rely on inbox's tx — DECIDE: simplest correct is inbox.ProcessOnce wraps the whole thing in a tx, and inside it the handler + outbox enqueue run on that tx (pg.FromContext sees it); so do NOT also wrap with Transaction (would be a redundant savepoint). Use: consumer → inbox.ProcessOnce(... handler-without-Transaction-behavior, but WITH Logging/Validation/Audit ...). Audit uses pg.FromContext → joins the inbox tx. Document this composition.
- main.go: wire config, log, telemetry, run.Closer, pg pool + Migrate, kafka client/consumer/producer, outbox repo + outboxkafka publisher + relay (Run in goroutine, registered with Closer), inbox, cqrs handler, audit store. EnsureTopics. Start consumer + relay; block on run.Run.
- Integration test in this service OR defer to Task 6 e2e. Add a focused test: produce a CreateOrderCommand to orders.commands, run the service's consumer wiring, assert an orders row + an OrderCreated on orders.events. (Can be in Task 6.)
- Commit `feat(examples/orders): command consumer with CQRS pipeline and transactional outbox`.

## Task 5 — gateway (REST edge + command publish + projection + query)
- DB: `orders_read(order_id uuid pk, customer_id, amount_cents, currency, status, updated_at)` (the projection/read model).
- API impl (implements oapi-codegen interface):
  - `POST /orders`: auth (principal required via auth middleware), validate request, generate order_id, publish CreateOrderCommand to "orders.commands" (kafka producer, key=order_id), return 202 {order_id}.
  - `GET /orders/{id}`: read from orders_read (sqlc GetOrderView); 404 if absent; else 200 OrderView. (Optionally cache via platform/cache + cqrs Caching behavior — optional; keep simple: direct read, or wrap with cache.)
- Projection consumer: consume "orders.events" + "payments.events" (inbox dedup): OrderCreated → upsert orders_read(status="created"); PaymentProcessed → update orders_read set status="paid". 
- httpserver with auth middleware (platform/auth) — for the demo, wire a Verifier; e2e test can use a stub Verifier OR the JWKS test pattern. Provide a config flag to disable auth for local/demo.
- main.go wires everything (httpserver, pg, kafka producer + projection consumer, auth, run.Closer, health incl pg+kafka). Serve openapi spec + Swagger UI (optional).
- Commit `feat(examples/gateway): REST edge publishing commands, event projection, query read model`.

## Notes
- Inbox-tx vs Transaction-behavior composition: when a consumer uses inbox.ProcessOnce (which opens a RunInTx), the command handler runs inside that tx; do NOT also apply the Transaction behavior (redundant savepoint) — apply Logging/Tracing/Metrics/Validation/Audit only. The gateway's POST path (no consumer/inbox) publishes a command directly (no DB tx needed for publish; 202 returned).
- Auth in e2e: use a stub `auth.Verifier` returning a fixed Principal for the bearer "test-token", or the httptest-JWKS pattern from SP5. Keep the gateway's Verifier pluggable.
- Topic naming: aggregateType in outbox == topic (orders.events, payments.events); commands topic "orders.commands".
- Each service owns its DB (separate database name) — DB-per-service.
